# Mini-Spec: fix-1993-mf-429

## Was ändert sich
- In `src/providers/meteofrance.py`, `fetch_thunder_signals_multi`, im `except httpx.HTTPStatusError`-Zweig (aktuell ~Zeile 699): HTTP 429 wird als eigener Fall erkannt, bevor er in den generischen „nicht abrufbar"-Pfad fällt.
- Bei 429 loggt der Code eine eigene Warnung, die die Drosselung benennt (z. B. „Blitzdichte +%dh gedrosselt (429) — Meteo-France-Limit erreicht"), statt der generischen Meldung „Blitzdichte +%dh nicht abrufbar: %s".
- Der Rückgabewert bleibt unverändert `None` für das betroffene Zeitfenster (Verhalten für Aufrufer/Grundvorhersage ändert sich nicht) — es ändert sich ausschließlich die Log-Aussage, damit ein 429 im Betrieb von echtem Datenausfall unterscheidbar ist.

## Was darf sich nicht ändern
- Kein Rückfall-/Retry-Verhalten für 429 (keine aktive Drosselung, kein Zähler/Warten — das bleibt bewusst außen vor, siehe Intake-Begründung).
- Der 404-Rückfallpfad (Lauf-Kandidaten) bleibt unverändert.
- Rückgabeform von `fetch_thunder_signals_multi` (Dict-Struktur, `None` bei Fehlschlag) bleibt identisch.
- Die zweite im Ticket genannte Lücke (gleichzeitige Abrufe im `thunder_window_cache`) wird NICHT angefasst — laut Ticket heute folgenlos.

## Acceptance Criteria

- **AC-1:** Given ein Blitzdichte-Abruf gegen Météo-France (`fr_direct`) für ein Zeitfenster, When die Antwort mit HTTP 429 fehlschlägt, Then loggt der Code für dieses Zeitfenster eine eigene, unterscheidbare Warnung (enthält „429" bzw. „gedrosselt"), nicht die generische „nicht abrufbar"-Meldung.
- **AC-2:** Given derselbe Abruf, When die Antwort mit einem anderen Fehlerstatus (z. B. 500) fehlschlägt, Then bleibt die bisherige generische „nicht abrufbar"-Meldung unverändert erhalten.
- **AC-3:** Given einen der beiden Fehlerfälle (429 oder 500), When der Abruf für das Zeitfenster fehlschlägt, Then bleibt der Rückgabewert für dieses Zeitfenster `None`, es findet kein Retry und keine aktive Drosselung statt.

## Manuelle Test-Schritte
1. Unit-Test simuliert `_request_once`, der eine `httpx.HTTPStatusError` mit `status_code=429` wirft.
2. Log-Ausgabe prüfen: enthält „429"/„gedrosselt" statt der generischen „nicht abrufbar"-Formulierung.
3. Rückgabewert für das betroffene Zeitfenster ist weiterhin `None`.
4. Gegenprobe mit einem anderen Fehlerstatus (z. B. 500): generische „nicht abrufbar"-Meldung bleibt wie bisher.
